SVG-MPPI 헤어핀 문제와 장애물 가이드 실험 노트

berlin 맵, 수업 컨테이너(misys:forza_full), 내 PC(i5-8500)에서 GUI 없이 돌린 실험 결과입니다. 실험 한 번은 300초(약 15~18랩)이고, 결과는 race_manager 전광판 기록(JSON/PNG) 그대로입니다.

요약

  • S자 막다른 길 문제의 원인을 찾아 해결했습니다. SVG-MPPI의 온도 파라미터 svg_mppi.lambda가 3.0이면 헤어핀 꼭짓점에서 좌회전(정답)과 우회전(막다른 주머니) 후보가 가중 평균에서 섞이고, 수가 많은 우회전 쪽으로 넘어갑니다. λ = 1.0으로 바꾸자 주머니 진입이 39랩 중 13회 → 44랩 중 0회, 클린 랩 평균이 17.4 s → 15.9 s가 됐습니다.
  • 예상했던 원인들(예측 구간이 짧다, 모델이 시뮬과 다르다, 헤어핀이 빠르다, 차체 크기가 크다)은 실험해 보니 모두 오히려 나빠지거나 효과가 없었습니다.
  • 장애물 회피의 가장 큰 개선은 충돌 지도 부풀림 방식입니다. 공식 방식(판단 시점 차 방향 상자)을 방향과 무관한 원형 반지름 0.15 m로 바꾸자, seed 5개 기준 충돌이 34 → 11회, 같은 시간 랩 수가 28 → 65가 됐습니다. 어떤 설정으로도 못 지나가던 헤어핀 꼭짓점 장애물 배치도 무충돌로 통과합니다.
  • 장애물 순서를 고려한 가이드 기준 경로(guide)를 구현했습니다. 빠른 구간의 장애물에는 효과가 있지만 헤어핀에서는 벽 충돌을 늘립니다. 헤어핀에서만 끄는 구간 표(학습 B안의 첫 사례)를 쓰면 seed 5개에서 69랩, 충돌 9회로 가장 좋았지만, guide 없이 원형 부풀림만 쓴 경우(65랩, 11회)와의 차이는 아직 우연일 수 있는 크기입니다. seed 추가 확인 필요
  • 원본 샘플 8000도 돌아가지만 내 PC에서는 약 20 Hz로 느려져 장애물 조건에서 더 나쁩니다. light(3000)를 유지하고, 평가 PC에서 다시 잽니다.
  • 주행 중 ros2 param set으로 파라미터를 바꾸는 기능, 구간별 자동 변경 노드, Optuna 학습 스크립트를 만들었습니다(학습은 아직 돌리지 않음).

1. S자 막다른 길(주머니) — 원인과 해결

왼쪽 위 헤어핀(s ≈ 24 m, 회전 반경 0.95 m)에서 차가 왼쪽으로 꺾지 않고 정면의 막다른 공간으로 들어가 한 바퀴 돈 뒤 역주행으로 빠져나오는 문제입니다. 기존 설정으로 재현하면 약 3랩에 1번꼴(+7.5 s)로 일어납니다.

무엇을 확인했나

문제가 생긴 순간을 기록해 보니, 실패한 랩도 s = 23.5 m까지는 조향·속도·횡오차가 정상 랩과 똑같았습니다. 꼭짓점(s ≈ 24 m)에서 MPPI 충돌률이 한 주기 만에 0.0 → 0.4~0.8로 뛰고, 같은 주기에 조향이 +0.2 rad(좌)에서 −0.3 rad(우)로 뒤집혔습니다. 차의 상태가 아니라 solver의 선택 문제라는 뜻입니다.

왜 λ인가

MPPI는 샘플 3000개를 굴려 보고, 충돌하지 않은 샘플을 exp(−비용/λ)로 가중 평균해 조향을 정합니다. 헤어핀 꼭짓점에서는

  • 올바른 좌회전 통로는 좁아서 충돌하지 않는 샘플이 적고(비용은 낮음),
  • 정면의 주머니는 넓어서 충돌하지 않는 샘플이 아주 많습니다(레이스라인에서 멀어서 비용은 조금 높음).

λ = 3이면 비용 차이가 가중치에 약하게 반영돼서 "수가 많은 오른쪽"이 평균을 끌고 갑니다. 좌우 두 모드가 섞인 평균이 오른쪽으로 넘어가는 순간 차가 주머니로 들어갑니다. λ = 1이면 비용이 가장 낮은 좌회전 샘플이 확실히 이깁니다(아래 그림: 상위 후보 400개가 모두 좌회전).

다른 실험 결과도 같은 방향으로 설명됩니다. 속도를 줄이면 오른쪽 샘플이 덜 멀리 가서 비용이 작아져 더 경쟁력이 생기고, 예측 구간을 늘리거나 모델을 정직하게 하면 좌회전 샘플이 더 많이 충돌로 판정돼 줄어듭니다.

교수님 피드백("SVG 선택을 어떻게 유도할지")과 바로 이어지는 결과입니다. SVG의 guide 입자가 방향을 골라도, 마지막 MPPI 가중 평균의 온도가 높으면 두 모드가 다시 섞입니다. 발표에서 "모드 선택 실패의 원인을 λ로 찾았다"를 근거 자료로 쓸 수 있습니다.

적용: 패키지의 svg_mppi.yaml, svg_mppi_light.yaml 모두 svg_mppi.lambda: 1.0으로 바꾸고 [변경 11/19] 표시를 남겼습니다. 공식 solver 코드는 그대로입니다.

2. 연속 장애물 — 가이드 기준 경로 (교수님 과제)

공식 solver는 guide 입자의 초기 방향을 바꾸는 API가 없습니다. 그래서 solver는 그대로 두고, solver가 따라가는 기준 경로 지도(reference SDF)를 장애물 열 전체를 보고 미리 옮겨 주는 방식으로 구현했습니다.

  1. 라이다 점 중 정적 지도 벽에서 떨어진 점 = 장애물. 같은 칸이 스캔 3번 이상 보여야 인정(오인식 0회 확인).
  2. 레이스라인 기준 Frenet 좌표(s, d)로 바꿔 앞쪽 6 m 안의 장애물 열을 한 번에 봅니다.
  3. 동적 계획법(DP)으로 "각 장애물을 어느 쪽으로 지나갈지" 순서를 한 번에 정합니다. 비용 = 레이스라인 이탈 + 가로 기울기 + 장애물·벽 여유 + 직전 계획 유지 + 한 번 정한 쪽 유지.
  4. 그만큼 옆으로 옮긴 레이스라인으로 기준 경로 지도를 만들면 SVG의 guide 입자와 샘플이 그 모드로 모입니다.

장애물이 없으면 원래 레이스라인을 그대로 씁니다. /drive는 여전히 SVG-MPPI 하나만 냅니다. 켜고 끄기: ros2 param set /svg_mppi guide.enable true

결과: seed 5개 비교 (λ 1.0, 장애물 4개, 조건마다 240 s × 5 = 20분 주행, PC 한가할 때)

"부풀림"은 충돌 지도에서 장애물·벽을 차 크기만큼 키우는 방식입니다. 공식(rigid)은 판단 시점 차 방향의 상자, 원형(circle)은 방향과 무관한 반지름 0.15 m입니다. seed = 2026, 11, 7, 42, 100.

  • 가장 큰 개선은 원형 0.15 부풀림입니다. 충돌 34 → 11회, 같은 시간 랩 수 28 → 65.
  • guide의 추가 효과는 아직 입증되지 않았습니다. 원형 위에 켜면 장애물 충돌은 10 → 7로 줄지만 벽 충돌이 1 → 9로 늘었습니다.
  • 실패 위치를 보면 둘의 약점이 다릅니다. guide를 끄면 seed 7의 빠른 구간(s ≈ 45~46.5, 오른쪽 큰 커브 끝)에서 같은 장애물에 6번 연속 부딪혔고, guide를 켜면 이 배치를 통과합니다. 반대로 guide를 켜면 충돌 16회 중 11회가 헤어핀(s 23~25.6)에서 납니다. 기준 경로를 바깥으로 옮기다 주머니 위쪽 벽에 닿습니다.
  • 그래서 F 조건은 param_scheduler.py로 헤어핀(s 21.5~27)에서만 guide를 끕니다. 학습 B안(구간별 파라미터)의 첫 사례입니다. 랩 수가 가장 많고(69) 충돌이 가장 적었습니다(9회). 헤어핀 벽 충돌이 사라졌고, seed 7의 빠른 구간 장애물도 14랩 모두 무충돌로 지나갔습니다.
  • 다만 C와의 차이(충돌 11 대 9)는 seed 5개로는 우연일 수 있는 크기입니다. seed를 늘려 확인해야 합니다.

재현: run_exp.sh <이름> params=configs/x_r15.yaml sched=configs/sched_guide_off_hairpin.yaml obs=4 seed=<seed> (x_r15 = light + λ 1.0 + guide 켬 + 원형 0.15)

헤어핀 꼭짓점 장애물이 다음 핵심 과제

seed 2026의 2랩째에는 장애물이 헤어핀 꼭짓점 바로 뒤(s = 24.6 m) 레이스라인 위에 놓입니다. 안쪽은 벽까지 0.46 m라 바깥(주머니 쪽)으로 돌아야 하는데, 충돌 지도가 장애물을 판단 시점의 차 방향 뒤쪽으로 0.47 m 늘려서 통로 입구를 통째로 막아 버립니다(충돌률 1.00). guide를 켜도 끄도 못 지나갑니다. 장애물이 랩마다 4개씩 무작위로 놓이므로, 균일 배치를 가정하면 이 구간(약 4 m)에 장애물이 걸리는 랩은 대략 3랩에 1번꼴로 예상됩니다.

대응으로 방향과 무관한 원형 부풀림 옵션(local_costmap.inflation_mode: circle)을 추가했습니다(위 표).

3. 학습은 어떻게 할까

A~C 안 모두 "학습"이라고 부를 수 있지만, 남은 4주와 시뮬 속도를 생각하면 범위를 정해야 합니다. 시뮬레이터는 0.01 s 벽시계 타이머로 돌아서 실시간보다 빠르게 돌릴 수 없고, 한 랩이 약 16 s라 1시간에 200랩 남짓입니다.

안판단이유
A. 고정 파라미터 튜닝채택베이지안 최적화(Optuna)는 trial 결과로 대리 모델을 학습해 다음 값을 고르는 방식이라 학습으로 설명할 수 있고, 하룻밤 수백 trial이면 충분합니다. λ 발견처럼 효과가 큽니다.
B. 상황별 파라미터채택 (A와 합침)맵이 고정이므로 "상황" = 트랙 구간(s) + 장애물 유무로 정의하면 깔끔합니다. 구간별 속도 배율과 장애물 모드 값을 A와 같은 방법으로 학습하고, 주행 중에는 그 표대로 자동 적용합니다.
C. 가이드 방향 학습대체방향 선택은 DP guide가 매 주기 최적으로 풀고, 학습은 guide의 가중치(여유 거리, 유지 비용)를 맞추는 데 씁니다. 방향 자체를 학습(모방/강화학습)하기에는 시뮬 횟수가 부족합니다.
D. 비용 가중치A에 포함λ, q_dist 같은 solver 값도 탐색 공간에 넣을 수 있습니다(바뀔 때 solver 재생성).

학습 절차 (준비된 도구)

  1. 평가 PC 기준으로 고정할 것을 먼저 고정: 샘플 수, 스레드 수, λ = 1.0. 학습은 평가 PC와 같은 사양인 학교 PC에서 돌립니다.
  2. 탐색 공간: configs/tune_space.yaml. 곡률로 나눈 5개 구간의 속도 배율, 장애물 근처 속도, guide 여유 거리·유지 비용 등 8개 값입니다.
  3. trial 하나: 시뮬을 계속 켜 둔 채 파라미터만 바꾸고, 다음 랩 경계부터 3랩을 달린 결과로 점수를 냅니다. 점수 = 평균 랩타임 + 5 × 충돌 + 10 × 복구.
  4. seed 분리: 학습용 seed와 검증용 seed를 따로 둡니다. 최종 표는 검증 seed 여러 개에서 다시 확인한 뒤 씁니다.
  5. 결과: tuning/<이름>_best_schedule.yaml. 이 표를 param_scheduler.py에 넣으면 주행 중 자동 적용됩니다. 결과 DB(sqlite)는 파일이라 PC를 옮겨도 이어서 돌릴 수 있습니다.
# 컨테이너: 시뮬+MPPI+race_manager 를 길게 띄워 두고 (예: 3시간)
bash ~/shared_dir/svg_mppi_exp/tools/run_exp.sh tune dur=10800 obs=4 seed=100 params=<설정.yaml>
# 다른 컨테이너 터미널: optuna 는 별도 venv (ROS의 numpy 를 건드리지 않게)
python3 -m venv --system-site-packages ~/shared_dir/svg_mppi_exp/venv
~/shared_dir/svg_mppi_exp/venv/bin/pip install optuna
~/shared_dir/svg_mppi_exp/venv/bin/python ~/shared_dir/svg_mppi_exp/tools/tune.py \
    --space ~/shared_dir/svg_mppi_exp/configs/tune_space.yaml --log-dir <run_exp 의 OUT 폴더> --trials 60

tune.py와 param_scheduler.py는 작성만 했고 실제 학습은 아직 돌리지 않았습니다. 구간별 속도 변경(param_scheduler)은 실험에서 동작을 확인했습니다.

4. 주행 중 파라미터 변경은 어떤 개념인가

두 가지를 구분하면 됩니다.

  • 학습은 평가 전에 시뮬에서 미리 합니다(오프라인). 결과물은 "상황 → 파라미터" 표 하나입니다.
  • 주행 중 변경은 그 표를 보고 param_scheduler.py가 구간이 바뀌거나 장애물이 보일 때 자동으로 파라미터를 넣는 것입니다. 주행하면서 새로 학습하는 온라인 학습은 아닙니다. 평가 중에 모델이 바뀌면 위험하고 재현도 안 됩니다.

평가 시연용으로 사람이 직접 바꾸는 것도 됩니다. 노드 쪽 값(속도 배율, guide.*)은 다음 주기부터 바로 반영됩니다. solver 값(λ, 공분산, 샘플 수, 예측 구간)은 새 solver를 백그라운드에서 만든 뒤 제어 주기 사이에 교체합니다(solver는 항상 1개, 교체 순간 웜스타트 초기화).

ros2 param set /svg_mppi reference_sdf.reference_speed_scale 1.2   # 전체 속도 +20%
ros2 param set /svg_mppi svg_mppi.lambda 1.0                        # 로그: "new solver built ..." → "solver swapped"
ros2 param set /svg_mppi guide.enable true

5. GUI 없이 돌린 결과와 GUI를 띄운 결과의 차이

물리와 판정은 같습니다. 시뮬레이터, 충돌 판정, 랩 계측은 GUI와 무관하게 같은 코드로 돌고, 전광판도 같은 JSON에서 그립니다. 차이는 CPU입니다. RViz는 시작할 때 코어 하나 가까이를 쓰고 이후에도 계속 일부를 씁니다. 그만큼 MPPI 계산 시간이 늘고 25 ms 주기를 넘기는 비율이 올라가서, 같은 설정이라도 결과가 달라질 수 있습니다.

얼마나 민감한지는 이번에 우연히 확인됐습니다. PC에서 다른 프로그램이 함께 돌자 같은 설정의 계산 시간이 평균 20 ms → 49 ms, 클린 랩 평균이 15.9 s → 17.8 s가 됐습니다. 내 PC(6코어)에서는 GUI 유무나 다른 프로그램이 결과를 바꿀 수 있으니, 비교 실험은 GUI 없이 PC가 한가할 때 돌리고, 평가 직전 확인은 평가 PC에서 GUI를 켠 상태로 하는 것이 맞습니다. 평가 PC(8코어 16스레드)에서는 차이가 작을 것으로 예상합니다.

같은 설정, 장애물 0, 150 s계산 평균상위 5%25 ms 초과클린 랩 평균
GUI 없음19.8 ms28.6 ms11%15.80 s
GUI (RViz + 전광판 창)23.5 ms32.4 ms31%15.77 s

GUI를 켜면 계산이 약 4 ms 늘고 주기를 넘기는 비율은 3배가 되지만, 장애물이 없으면 랩타임은 같았습니다. 장애물 회피처럼 빠른 반응이 필요한 상황에서는 차이가 날 수 있어, 비교 실험은 GUI 없이 돌립니다.

6. 전광판

race_manager가 실행마다 결과를 JSON으로 쌓고 ros2 run race_manager report --no-show로 평가 때와 같은 전광판 PNG를 만듭니다. 실험 도구(run_exp.sh)가 실행이 끝날 때마다 이것을 자동으로 만들어서, 실험 하나가 끝나면 전광판 그림으로 보고합니다(위 1번의 두 그림).
